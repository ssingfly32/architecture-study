# 부하테스트 결과: N+1 개선 전/후 비교 (JMeter + 리소스 모니터링)

- 대상 API: `GET /posts`
- 시나리오: 동시 사용자(VU) 10 → 50 → 100 → 200 → 400, 각 단계 30초 유지 (`loadtest/jmeter/get-posts.jmx`)
- 서버 환경: Docker 컨테이너, 1 Core / 2GB RAM 제한 (`docker-compose.yml`)
- DB: 동일한 PostgreSQL 데이터(게시글 10,000건 + 댓글 30,000건, `scripts/seed.sql`)를 before/after 양쪽에서 그대로 재사용 → 코드 차이 외 변수 제거
- Before: `12732b1` (N+1 존재, QueryDSL 적용 전) / After: 현재 브랜치 (`9af19d5`에서 QueryDSL LEFT JOIN + GROUP BY로 개선)
- 원본 데이터: `loadtest/results-before/`(before.jtl, resources.csv, before-actuator.jtl, before-actuator-resources.csv), `loadtest/results-after-jmeter/`(after.jtl, resources.csv)

|---|---|---|

| 에러율 | **95.87%** (720건) | **0%** |
| 평균 응답시간 | 40,642ms | 3,384ms |

| CPU (docker stats) | 최대 100%까지 스파이크성 | 50 VU 단계부터 **100%에 고정 지속** |

Before 커밋(`12732b1`)엔 원래 Actuator가 없어서, N+1 버그 자체와 무관한 Actuator 의존성만 임시로 추가한 별도 이미지(`archstudy-before-actuator`)를 새로 빌드해 **동일한 VU 10→50→100→200→400 부하 시나리오(`get-posts.jmx`)로 재실행**하며 측정했다 (`loadtest/results-before/before-actuator.jtl`, `before-actuator-resources.csv`). 다만 이 재실행에서도 요청의 95% 이상이 실제 쿼리 실행 없이 커넥션 풀 대기 중 타임아웃으로 실패했으므로, 이 힙 증가는 "N+1 쿼리 결과를 많이 들고 있어서"라기보다 대기 중인 스레드/커넥션 관련 객체가 쌓인 결과로 보는 게 타당하다 (heap dump로 직접 확인한 건 아니고, 실패 비율로 미루어 본 추정이다). After와 힙 범위 자체는 비슷하지만, 그 의미는 다르다.

## Saturation Point 특정

Saturation Point는 "동시 사용자를 늘려도 처리량(TPS)이 더 안 늘어나는 지점"이다. 아래 세 가지 신호가 같은 지점에서 겹치면 그 지점을 Saturation Point로 확정할 수 있다: ① TPS 곡선이 꺾여서 평평해지는 지점, ② 응답시간이 완만하다가 급격히 치솟기 시작하는 지점, ③ 리소스(CPU/메모리)가 100%에 붙는 지점.

**Before (VU별 TPS): 10 → 0.0 / 50 → 2.5 / 100 → 6.3 / 200 → 6.3 / 400 → 6.3**

VU 10에서 이미 요청이 거의 완료되지 못하고(59초 동안 1건), VU 50부터는 에러율이 93%를 넘는다. TPS는 6.3/s 근처에서 벗어나지 못한다. → **Saturation Point는 VU 10~50 사이에서 이미 발생** (원인: HikariCP 커넥션 풀 10개 고갈).

**After (VU별 TPS): 10 → 13.2 / 50 → 30.8 / 100 → 38.7 / 200 → 38.0 / 400 → 34.8**

VU 10→50 구간은 TPS가 13.2→30.8(+133%)로 가파르게 늘지만, 50→100 구간은 30.8→38.7(+26%)로 증가폭이 꺾이고, 100→200 구간은 38.7→38.0으로 사실상 정체(오히려 미세 하락)한다. CPU 사용률은 이보다 조금 먼저, **50 VU 단계 중반(약 35~42초 지점)부터 이미 100%에 붙기 시작**해서 100 VU 단계가 시작될 때는 이미 완전히 포화된 상태다 — 즉 리소스(CPU)가 먼저 한계에 도달하고, 그 여파로 처리량(TPS)이 뒤따라 꺾이는 순서다. 세 신호(CPU 포화, TPS 정체, 응답시간 급증)가 50~100 VU 구간에서 연쇄적으로 겹치므로 → **Saturation Point ≈ VU 100 (TPS 약 38~39/s, CPU 포화가 원인)**.

**비교:** N+1 개선 전엔 Saturation Point가 VU 10~50 구간(TPS 한계 6.3/s, DB 커넥션 풀 고갈)이었고, 개선 후엔 VU 100 구간(TPS 한계 약 39/s, CPU 포화)으로 밀려났다. 같은 1코어 환경에서 처리 가능한 동시 사용자 규모와 처리량이 크게 늘어난 것이다.

## 핵심 발견: Saturation Point가 발생하는 "지점" 자체가 이동함

### Before: DB 커넥션 풀 고갈이 원인

Before 상태 컨테이너 로그(`docker logs archstudy-before`)를 확인한 결과, 실패의 정확한 원인이 나왔다:

```
java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available,
request timed out after 30000ms (total=10, active=10, idle=0, waiting=189)
```

HikariCP 커넥션 풀(기본 크기 10)이 꽉 찬 채로 최대 189개 요청이 대기하다가, HikariCP 기본 타임아웃(`connectionTimeout`, 30초) 시점에 전부 예외로 실패했다. 응답시간 최소값이 정확히 `30,011ms`인 것도 이 타임아웃 값과 정확히 일치한다 — 즉 "느린 응답"이 아니라 "커넥션을 못 받아서 실패한 요청"이 대부분이었다는 뜻이다.

**왜 이렇게 되는가:** N+1은 단순히 "쿼리 개수가 많아서 느리다"에서 끝나지 않는다. `GET /posts` 요청 하나가 1(목록 조회) + N(게시글별 댓글 수 조회) 개의 쿼리를 순차적으로 실행하는 동안, 그 요청은 DB 커넥션을 계속 붙잡고 있다. 동시 요청 수가 늘어나면 "커넥션을 오래 붙잡는 요청 수 × 동시성"이 풀 크기(10)를 순식간에 초과하고, 커넥션 풀은 초과분을 큐잉하다가 하드 타임아웃으로 끊어버리는 구조이기 때문에 완만하게 느려지는 대신 절벽처럼 무너진다.

### After: 병목이 DB에서 CPU로 이동

LEFT JOIN + GROUP BY로 요청당 쿼리를 1개로 줄이면서 커넥션 보유 시간이 극히 짧아졌고, 그 결과 커넥션 풀은 더 이상 병목이 아니게 됐다 (에러 0%, Hikari 타임아웃 로그 없음).

대신 `resources.csv`를 보면 50 VU 단계가 진행되는 중(약 18:19:26, 테스트 시작 후 42초 지점)부터 **CPU 사용률이 100%에 고정**된다 — 1코어 컨테이너 환경이라 병목이 완전히 CPU로 옮겨간 것이다. 응답시간이 400 VU 구간에서 평균 9.7초까지 늘어나는 것은 실패가 아니라, CPU가 포화된 상태에서 요청들이 정상적으로 큐잉되며 순차 처리되는 graceful degradation이다. JVM 힙은 40~460MB 사이를 오가며(GC로 인한 톱니파형) 2GB 제한 대비 여유가 커서, 메모리는 병목이 아니었다.

## 결론

N+1을 고치기 전엔 병목이 "DB 커넥션 풀"이었고, 고친 후엔 병목이 "CPU 코어 수"로 이동했다. Saturation Point 분석은 한 번 병목을 없애면 다음 병목이 드러나는 과정이라는 걸 보여준다.

단, "다음 병목이 CPU였다"는 건 이 앱의 절대적인 특성이 아니라 **서버를 Docker 1 Core / 2GB로 제한한 이번 테스트 조건에 종속된 결과**다. Before 상태는 병목(DB 커넥션 풀 고갈)이 워낙 압도적이어서 코어를 몇 개 줬어도 결과가 크게 다르지 않았을 것이다 — 요청이 CPU를 쓰기도 전에 커넥션을 못 받아 타임아웃으로 죽었기 때문이다. 반면 After 상태는 그 병목을 치우고 나서야 "1코어라는 제약 안에서" 그다음으로 약한 고리가 드러난 것이다.

## 부록: 직접 실행한 라이브 모니터링 (After 상태 재확인)

위 After 측정은 JMeter를 headless로 돌리면서 CPU/메모리 변화를 사후에 확인한 것이었는데, 이번엔 **직접 부하테스트를 실행하면서 리소스 변화를 실시간에 가깝게 관찰**하는 방식으로 다시 확인했다.

- 방법: `docker stats architecture-study-app`를 2초 간격으로 기록 + `run-loadtest.bat`으로 동일한 `.jmx`(VU 10→50→100→200→400)를 직접 실행
- JMeter 자체 리포트(`-e -o` 옵션으로 생성되는 내장 HTML 대시보드, 플러그인 불필요): `loadtest/jmeter/report/index.html`
- 원본 데이터: `loadtest/jmeter/result.jtl`, `loadtest/jmeter/live-resources.csv`, `loadtest/jmeter/live-response-buckets.csv`

**결과 (5,011건 요청, 에러 0건):**

| 지표 | 값 |
|---|---|
| Peak CPU | 109.8% (1코어 한계 초과) |
| Peak Memory | 55.2% (2GB 중 ~1.1GB) |
| 평균 응답시간 | 3,080ms |
| P95 응답시간 | 10,363ms |
| 최대 응답시간 | 25,087ms |

앞서 측정한 After 결과(평균 3,384ms, 에러 0%)와 거의 동일한 패턴으로 재현됐다 — CPU가 50 VU 단계 중(약 38초 지점)부터 100% 근처에 눌러붙고, 그 이후 응답시간이 완만하게 늘어나는 graceful degradation. 같은 조건에서 반복 실행해도 결과가 일관되게 나온다는 것도 확인된 셈이다.

**추가로 확인된 병목 후보:** 이 과정에서 (지금은 제거한) Prometheus+Grafana로 JVM 지표를 잠깐 들여다봤을 때, `jvm_threads_live_threads`가 정확히 **200에서 평평하게 막히는** 게 관찰됐다. 이건 Spring Boot(Tomcat) 기본 설정값 `server.tomcat.threads.max=200`과 일치한다. 즉 400 VU까지 요청이 몰려도 서버는 동시에 최대 200개까지만 실제로 처리하고 나머지는 Tomcat 내부 큐에서 대기한다 — CPU 1코어 제한과 별개로, Tomcat 스레드 풀 크기도 400 VU 구간의 응답시간 증가에 함께 기여하는 요인이다.
